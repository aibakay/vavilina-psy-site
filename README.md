# Сайт Полины Вавилиной

Статический сайт на [Eleventy (11ty)](https://www.11ty.dev/): страницы собираются
из JSON-файлов в `src/`, содержимое правится через панель Sveltia CMS с входом по
паролю. Базы данных нет. Работает в Docker-контейнере на Timeweb Cloud VPS за
обратным прокси.

## Структура

| Путь | Что это |
|---|---|
| `src/` | контент (JSON) и шаблоны, из которых собирается сайт |
| `.eleventy.js` | конфигурация сборки |
| `admin/` | панель редактирования (Sveltia CMS) |
| `api/auth.js` | вход в панель по паролю |
| `lib/rate-limit.js` | ограничение попыток входа (см. «Scaling») |
| `server.js` | продакшн-сервер: статика из `_site` + `/api/auth` |
| `_site/` | результат сборки (в репозиторий не коммитится) |

## Команды

```bash
npm install
npm run dev     # локальная сборка с автообновлением
npm run build   # сборка в _site/
npm start       # запуск server.js (нужен собранный _site/)
npm test        # тесты
```

## Переменные окружения

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `GITHUB_TOKEN` | да | — | fine-grained PAT для коммитов из панели |
| `ADMIN_PASSWORD` | да | — | пароль входа в панель |
| `PORT` | нет | `3000` | порт `server.js` |
| `AUTH_MAX_ATTEMPTS` | нет | `10` | попыток входа на IP за окно |
| `AUTH_WINDOW_MS` | нет | `900000` | длина окна лимита, мс (15 минут) |
| `AUTH_RATE_LIMIT_DIR` | нет | `<tmp>/vavilina-auth-rate-limit` | каталог со счётчиками попыток |
| `AUTH_RATE_LIMIT_STORE` | нет | `file` | `file` или `memory` (см. ниже) |

Подробности про настройку панели, запуск контейнера и обновление сайта —
в [ADMIN.md](ADMIN.md).

## Scaling

Раздел про то, что ломается при запуске сайта больше чем в одном процессе.
Сборка статики масштабируется как угодно — вопрос только в состоянии, а
состояние здесь ровно одно: **счётчик попыток входа в панель**.

### Как устроено ограничение попыток

`lib/rate-limit.js` пропускает не больше `AUTH_MAX_ATTEMPTS` POST-запросов на
`/api/auth` с одного IP за `AUTH_WINDOW_MS`. Сверх лимита — `429` с заголовком
`Retry-After`. GET (показ формы) не лимитируется.

Счётчик хранится **в файлах**, в каталоге `AUTH_RATE_LIMIT_DIR`: один файл на
пару (окно, IP), одна попытка — один байт в конце файла, число попыток — размер
файла. Дозапись такого размера атомарна (`O_APPEND`), поэтому блокировки не
нужны, а параллельные процессы не затирают друг друга. Файлы прошлых окон
удаляются попутно, не чаще раза в окно.

Раньше счётчик жил в `Map` в памяти процесса. Это работало ровно до второго
процесса: в cluster mode (PM2) или при нескольких контейнерах перебирающий
пароль попадал на соседнего воркера и получал лимит заново — то есть лимита
фактически не было. Файловый счётчик это чинит.

### Что масштабируется, а что нет

| Схема запуска | Лимит общий? | Комментарий |
|---|---|---|
| Один процесс | да | — |
| PM2 / `cluster`, несколько воркеров на хосте | **да** | у процессов общий `AUTH_RATE_LIMIT_DIR` |
| Несколько контейнеров на одном хосте | **да**, если смонтировать общий том в `AUTH_RATE_LIMIT_DIR` | без общего тома — у каждого свой счётчик |
| Реплики на разных хостах | **нет** | общей файловой системы нет |
| Serverless (Vercel и подобные) | **нет** | у каждого инстанса свой `/tmp`, инстансы эфемерны |

Важное ограничение: общий каталог — это общая файловая система. Дальше одного
хоста файловый счётчик не работает **by design**.

### Если понадобится несколько хостов

Пока сайт живёт на одном VPS — а он живёт именно так — ничего делать не нужно.
Признак, что пора: **больше одного хоста за балансировщиком**. Два пути, по
возрастанию надёжности.

**1. Sticky sessions (быстро, полумера).** Прибить клиента к одному бэкенду по
IP — тогда все его попытки считает один процесс:

```nginx
upstream site {
    ip_hash;               # запросы с одного IP идут на один бэкенд
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;
}
```

Дёшево, но лечит симптом: при смене состава бэкендов привязка перестраивается и
счётчики теряются, а клиенты за одним NAT попадают на один бэкенд целиком.
Вариант годится как затычка на время переезда, не как решение.

**2. Внешнее хранилище (правильно).** Вынести счётчик в Redis. Менять нужно
только `lib/rate-limit.js` — у него наружу торчат две функции, `consume(key)` и
`clientIp(req)`, а `api/auth.js` про устройство хранилища ничего не знает:

```js
// внутри lib/rate-limit.js, вместо fileStore
const redis = require("redis").createClient({ url: process.env.REDIS_URL });

async function redisStore(key, now) {
  const index = Math.floor(now / WINDOW_MS);
  const bucket = `auth:${index}:${hashKey(key)}`;
  const count = await redis.incr(bucket);          // атомарно на стороне Redis
  if (count === 1) await redis.pExpire(bucket, WINDOW_MS);
  return { count, resetAt: (index + 1) * WINDOW_MS };
}
```

Схема ключей та же, что у файлов (окно + хэш IP), так что логика вокруг не
меняется — кроме того, что `consume` станет асинхронной, а вызов в `api/auth.js`
получит `await`. Redis сам чистит ключи по TTL, поэтому подметание не нужно.

Готовая альтернатива, если не хочется писать самим, — `express-rate-limit` с
адаптером `rate-limit-redis`. Сейчас он не взят по одной причине: Redis в
инфраструктуре нет, а ради одного счётчика на одном VPS поднимать его и тянуть
зависимости незачем. Как только Redis появится — это разумный вариант, лимитер
переедет в middleware `server.js`, а `lib/rate-limit.js` уйдёт целиком.

### Аварийный режим

Если каталог со счётчиками недоступен (файловая система только для чтения, нет
прав, кончилось место), лимитер не роняет вход, а пишет в лог и переключается на
счётчик в памяти процесса — с оговоркой, что лимит перестал быть общим. Тот же
режим включается принудительно через `AUTH_RATE_LIMIT_STORE=memory`.

### Проверка

Сценарий «лимитер держит общий лимит на нескольких процессах» покрыт тестами:

```bash
npm test
```

Тест запускает 4 отдельных процесса, каждый делает 25 попыток с одного IP, и
проверяет, что суммарно прошло ровно `AUTH_MAX_ATTEMPTS`, а не в четыре раза
больше. Соседний тест фиксирует обратное поведение режима `memory` — тот самый
обход лимита переключением воркера.
